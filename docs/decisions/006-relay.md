# 006: the relay is a queue that orders blobs and knows nothing else

**Status.** Accepted; in the tree as `crates/relay`, `RelayCarrier` and `unheld relay new`. Written before the code (TRACE.md, R1), then amended for three things the code decided: the wire format, the storage layout and what an idle queue is. How a conversation's queues are shaped, one per direction between two people and one for a group, is `008-queue-per-direction.md`.

**Laws touched.** L19 (ordered or small) gains its first ordered carrier; L2 (zero custody), L7 (unlinkability), L12 (detectable omission), L13 (bounded state) and L22 (no creator input) constrain its shape. Reopens `002-carrier-view.md` as that note said it would.

## The question

Every carrier in the tree is a file, a pipe or the clipboard, none of which orders anything, so a group above `config::group::SMALL` is refused everywhere and the laws for large groups are a refusal rather than a system. Messaging Layer Security needs one total order on commits, and the cheapest thing that supplies one is a server. The question is how to add a server to a design whose first principle is that nobody holds anything, and the answer has to be that the server is a `Carrier` like the clipboard, in the adversary's position from the first line of its code, and that everything it can do is already something the clipboard can do, plus assigning numbers.

## The decision

**A relay is a store of queues, and a queue is a numbered sequence of blobs.** A queue has a random 32-byte identifier, a write capability and a read capability, each 32 random bytes made by the client that creates the queue, which hands the relay a hash of each and keeps the preimages. A `put` presents the write capability and a blob whose length is a bucket, and the relay appends it and answers with its sequence number, assigned on acceptance and dense from one. A `get` presents the read capability and the last sequence number seen, and the relay answers with the next blob and its number, or with nothing. A queue is deleted by its reader or expires untouched after a configured time, and the relay forgets it. That is the whole protocol: four verbs counting creation, each one frame of fixed-width fields with the blob last, over Transport Layer Security on a plain socket, which an onion service carries as it is. A hypertext layer was considered and bought the three verbs nothing but two crates, and the frame parser is a fuzz target like every other parser that reads bytes from outside.

**The order is the relay's, and that is the point.** Within one queue the relay's acceptance order is the total order, every reader sees the same numbers, and a group's `Carrier` over such a queue answers `true` from `ordered()`, so `start` and `add` pass the bound of L19. A relay that assigns different orders to different readers has forked the group, and MLS makes that fork a refusal on one side with the next message, exactly as a crossing commit does today over a file. A relay can therefore do to a large group what a clipboard can do to a small one and nothing worse, and the open gap in TRACE.md narrows from "no ordered carrier" to "a fork is detected and not repaired".

**It depends on `unheld-blob` and on nothing that can name a key.** The relay parses a blob only to check that its length is a bucket, and the client side, `RelayCarrier`, lives in the carriers crate under the same `cargo deny` ban on the core. The capabilities are random bytes compared in constant time against stored hashes; they are not keys in the kernel's sense, open nothing, and are held by the carrier in its own configuration, never in the vault. A reader with a capability learns the ciphertext it was already going to be sent, a writer with one can append blobs that `open` refuses, and neither can produce a roster change (L16), a message that opens as someone (`no_impersonation`), or a plaintext (L2). The transport authenticates the relay by a pinned certificate fingerprint that travels in the queue address, so the web public key infrastructure is not a party, and the address is handed over the way a file path is today: out of band, beside the welcome. The TLS implementation is rustls with graviola, the pure Rust provider from the rustls maintainers, so the client has no C cryptography and the `cargo deny` bans on ring and openssl stand; this is the one dependency the transport forced, and its reason is written beside those bans.

**The relay has no voice.** Its answers are blobs, sequence numbers and refusals, and the client interprets nothing else, so there is no field for a version to recommend, a configuration to push or a client to disable (L22). It has no accounts, no directory, no names and no logs, and the only state it keeps is the queues and their expiry. It is one static binary, and the client's list of relays is a file the person edits. A relay the maintainers run is a convenience with the same standing as any other.

**What it sees is stated and bounded.** A relay sees the bucket sizes, the times, the network addresses of writers and readers until the onion transport arrives, and that every blob in one queue belongs to one conversation. That last is the linkage `002-carrier-view.md` deferred to this note: the session identifier that MLS leaves readable inside the padding is now joined by a queue identifier outside it, and both say the same thing, which is that these blobs are one conversation to a carrier that already carries that conversation. It is accepted for the relay as it was for the overlay, with rotation of queues on a schedule the remedy and the open item below. A relay also learns how many readers collect from one queue, since the read capability is shared, which is a bound on the roster size and not its members. An unknown queue, a wrong capability and an identifier already taken get one answer, so a probe learns nothing about which queues exist.

**Floods are bounded by the relay and refused by the client.** A queue has a maximum depth and a maximum rate, both configuration, and a blob above the largest bucket is refused at the door, so a writer holding a capability, including a member the admin removed who still has the queue's write capability, can fill a queue and nothing else; the members' clients refuse what they cannot open and count it (L13), and the admin moves the group to a fresh queue by hand. Dropped blobs appear to every reader as a hole in the dense sequence, which the carrier reports before the core's own detection in `Msg` does (L12).

**Storage is a directory per queue, a file per blob, and needs no index.** A blob's file is named by its number, the two capability hashes sit beside them, and the count of blob files is the next number, so the relay needs the standard library to store things and no database. A queue is idle when its last put is older than the limit; reads do not keep it alive. A relay that restarts delivers what it had, and a relay whose disk is taken yields ciphertext that every carrier already had.

## What is in the tree

- `unheld-relay`, the crate: the store, the wire format, the pinned TLS identity, the server, and `RelayCarrier`, re-exported by `unheld-carriers`, with the queue address, both capabilities and the read cursor in a file of its own and `ordered()` answering `true`. The crate is under the same `cargo deny` policy as the client and the same rule test as the carriers: it depends on `unheld-blob` and on nothing that can name a key.
- `unheld-relay init` and `serve`, the binary (`docs/RELAY.md`), and `unheld relay new`, which makes a queue and writes its file.
- `LocalTransport`, a relay in process with an adversary at the switches, and the tests: the cursor catches a drop, a swap and a replay pass the carrier and are left to the core, a group one above the bound forms over the relay and is refused over a file, and a reader whose relay serves two commits the other way round refuses the first, applies the second, and is then out of step for good (`crates/cli/tests/relay.rs`).
- The frame parser as a fuzz target, `relay_wire`, and the TRACE.md rows for L12, L13 and L19.

## What is not here

Queue rotation on a schedule, which is the remedy for queue-level linkage, and with it a way for a group to move to a new queue inside a commit rather than by hand. The onion transport, which is what hides network addresses from the relay and is a later note of its own. Cover traffic, which would let a relay not tell a message from silence. Several relays per conversation, which is what makes blocking expensive. Persistence of the read cursor across a person's devices, which today is one carrier file per device. Whether a relay should accept the first `put` to an unknown queue as its creation, which is convenient and invites abuse, is decided at implementation by measuring the abuse. Each of these is a note, and none of them changes the three verbs.
